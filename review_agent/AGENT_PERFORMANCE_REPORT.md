结论：以本地 transcript 统计为准的"校对会话净消耗"为 331.3 M（raw）；面板数字为套餐口径（含促销折算/缓存计费规则/其他会话），两者不矛盾。**不要把主智能体与旁路任务混入校对统计**——本报告已按 profileId 隔离。

## 十、给其他使用者的建议

1. **按块分派 + 租约防撞**（claim/release + 文件锁）是多代理写同一账本的最稳形态；分区器以账本实际状态为准，天然自愈漏提交。
2. **确定性自检先跑一遍**再派 LLM（本次省约 9% 行数，零 token）。
3. **批量命令是弱模型提速的第一杠杆**：调用/行 从 1.5 → 0.18。
4. **上下文按任务包封顶**（100–150 行/代理）比"大包+续跑"更可控。
5. 碎块（1–5 行）固定开销摊不薄，收尾阶段可考虑提高单代理块数上限或合并提交路径。
6. 进度日志、账本均追加式 + 最新优先，配合主智能体波间合并，全程零账本损坏（0 坏行）。

## 十一、后校对阶段性能优化（rt.py 工具层）

全量校对完成后，对 rt.py 做了三项工具层优化，效果立竿见影：

### 1. Pickle 索引缓存

| 指标 | 优化前 | 优化后 |
|---|---|---|
| 每次调用（索引重建） | ~3.5s | — |
| 首次调用（建缓存） | — | ~3.8s |
| 后续调用（缓存命中） | — | **~0.71s（5 倍提速）** |
| findmany（批量 50 条） | — | **~0.75s（15ms/条）** |

实现：vid_idx / norm_list / unvoiced_norms / extra / BLOCK_KEYS 五个索引结构全量 pickle 到 `review_pack/.rt_cache_v{N}.pkl`；源文件 mtime 变化自动失效重建。并发保护：tmp 文件 + `os.replace` 原子写；后到进程检测新鲜 tmp 后等待（0.5s 轮询，60s 超时），只有一个进程实际建缓存。并发 3 进程实测：3.8s（一个建 + 两个等后命中）。

### 2. find 支持无语音 EVO 台词

原 find 只索引带 voice_id 的行，导致大量「EVO 有台词但未配音」的行判为 UNRESOLVED 而非 NO_VOICE。修复后无语音行入索引（`vid: null, voiced: false, note: "EVO有此台词行但未配音(NO_VOICE)"`），Agent 可正确区分两类。

### 3. 参数校验（消灭静默空结果）

| 错误输入 | 优化前 | 优化后 |
|---|---|---|
| `--char xyz`（非3位数字） | 静默返回空 hits | 报错：`--char 须为3位数字角色码` |
| `--scene T0133`（传了场景名） | 静默返回空 hits | 报错并提示用 `--evoscene` |
| `--evoscene ZZZ`（不存在的场景） | 静默返回空 hits | 报错：`不是有效EVO结构场景名` |
| `find ""`（空文本） | sim=100 命中（bug） | 报错：`归一化后不足2字符` |

find/findmany 共用 do_find 校验逻辑。

### 4. MCP Server 评估结论

工具执行占代理总时长仅 ~2%（20.5 次 × 0.7s = 14s vs 代理时长 714s），剩余 98% 为 LLM 思考延迟。MCP 能省的 2% 不值得引入持久进程维护成本。**结论：不需要 MCP**。批量命令 + pickle 缓存已将工具层优化到足够快。

## 十二、UNRESOLVED 批量再分类（缓存索引驱动，零 LLM）

全量校对结束后，用 pickle 缓存的 norm_list 索引（含无语音行）对 10,749 条 UNRESOLVED 做快速再分类——**2 秒跑完，零 LLM 调用**（Agent 重审需 133M token、约 500 元）。

### 再分类结果

| 再分类 | 行数 | 占比 | 含义 |
|---|---|---|---|
| **NO_VOICE** | **9,073** | **84.4%** | EVO 有台词行但未配音（Remake 新增配音） |
| MISSED_MATCH → FOUND | 4 | 0.04% | 同角色唯一 sim=100 命中，Agent 漏检 |
| MISSED_MATCH → CANDIDATES | 21 | 0.2% | 同角色多候选 |
| MISSED_MATCH → 维持 UNRESOLVED | 71 | 0.7% | 异角色泛用句，不可配 |
| **真 UNRESOLVED** | **1,591** | **14.8%** | EVO 确实无此文本（Remake 完全新写台词） |

### 根因

原 find 工具只索引带 voice_id 的行，Agent 按任务书规则正确判了 UNRESOLVED（「find 无命中」），但无法感知「EVO 有行无音」这种情况。find 增强后此分类错误不再发生。
