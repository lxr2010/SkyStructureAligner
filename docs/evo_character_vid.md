# EVO 角色与语音 ID（vid）的关系

> 本文说明 EVO 侧"谁在说话"的完整判定模型。
> 结论全部来自 EVO 日文本体原始剧本（`sc-evo-jp.vpk` 解包的 `SCENARIO/1/*.BIN`）
> 的静态分析，已在 `evo_speaker_full.csv` / `evo_bank_index_sc.json` 等数据中落地。

## 1. 语音 ID 的结构

EVO 每条带语音的台词有一个 10 位语音 ID（vid），与语音文件一一对应：

```
001 035 0604        文件: DATA_SC/TALK/035/CH0010350604.AT9
└┬┘ └┬┘ └─┬─┘
 │  │   └── 录音序号（场景内第几条）
 │  └────── 场景组/章节号（3位，即语音目录名）
 └───────── 角色语音 bank（3位，说话人身份的权威编码）
```

- vid 在剧本中形如 `0010350604V`（尾部 `V` 为标记）；
- `bank = vid[:3]`，是**全局角色语音库编号**，与角色一一对应；
- 语音文件按"场景组"分目录，文件名 = `CH` + 完整 vid。

## 2. bank 与角色的对应关系

**bank 是说话人身份的权威来源**，但注意：

- bank 编号**不是** T_NAME（角色名表）的记录序号。主角团前 8 个恰好接近
  （001=エステル…008=ジン），但从 009 起两套编号独立
  （例：ジョゼット T_NAME 序号 11，bank=009；リシャール bank=014）；
- 一个角色一个 bank，299 个 bank 覆盖全部语音（含群众/士兵等多人共用码）；
- bank → 角色名的三条推导路径（按可信度排序）：

| 路径 | 原理 | 覆盖 |
|---|---|---|
| char_id 槽位 + T_NAME | `0x100+n` 对话槽=全局角色 ID，bank↔char_id 100% 一致（见 §3） | 15 个主力角色 |
| 文本鉴别 | 台词自称/文体（例：022「レンの準備も終わり」=レン） | 7 个 |
| 采样鉴别（人工/AI 读台词） | 兜底，逐步补全中 | 其余多为共用码 |

已确认的对应（截至本文写作）：

```
001=エステル  002=ヨシュア   003=シェラザード  004=オリビエ
005=アガット  006=クローゼ   007=ティータ      008=ジン
009=ジョゼット 011=ミュラー少佐 012=アネラス  014=リシャール
015=ワイスマン教授 018=ケビン神父 020=痩せ狼ヴァルター 022=レン
028=ドロシー 030=ジョゼット(备注: 应复核) 033=クルツ 062=カシウス …
```

## 3. speaker（对话槽）的语义——为什么不能直接查场景字符串表

剧本里每条台词的 speaker 值分四类（s2 产物的 `speaker_kind` 字段）：

| speaker 值 | 语义 | 名字来源 | 可靠性 |
|---|---|---|---|
| `0xFE` | 旁白（无名牌头，可带语音） | 无 | — |
| `0xFF` | 系统文本；终章等处被多角色轮流使用 | 无 | — |
| `0x100+n` | **全局角色 ID**（T_NAME[n]，全游戏统一） | EVO T_NAME 直接查表 | 100%（实测跨场景零例外） |
| `0x8~0x5F` | 场景演员槽（选角随场景） | **只能靠 bank** | 槽位名不可信 |

关键教训：场景字符串表（BuildStringList 前几项）是**地图摆放模型**的名字列表
（含 `NpcIndex=0x181` 的装饰性主角团立牌），与对话槽编号**属于两套不相干的索引**。
拿"字符串表第 n 项"去解 `0x10x` 会张冠李戴
（实例：T0121 的 `0x103` 表名"アガット"，实际台词「フフ、さすが耳が早いわね」
是シェラザード——因为 0x103 = 全局角色 3）。

`0x100+n` 槽与 bank 的全局一致性（每组 100% 纯度）：

```
char1→001  char2→002  char3→003  char4→004  char5→006  char6→005
char7→007  char8→008  char9→018  char10→012 char11→009 char12→011
char14→033 char15→010
```

（注意 5/6 互换：槽位编号按 T_NAME 顺序，bank 按配音选角顺序。）

## 4. 特殊情况

- **演员槽乱入**：主角团未入队/离队时以剧情演员身份登场，挂在 `0x8~0x5F`
  小值槽上，但 bank 仍是自己的（实例：C1103 阿加特乱入对峙理查德，
  `0x9`+bank005，共 747 条此类记录）。**bank 始终忠实标识"谁的声音"**；
- **同槽多角色**：一个场景的不同剧情段可复用同一槽位（C5400 的 `0x101`
  交替承载エステル与レン）；`0xFF` 叙述框下多角色轮流（每行各自 bank）。
  这些都是逐行静态写死的，非运行时动态——判定粒度必须到"行"；
- **别名/幻影显示名**：显示名与语音是两条独立通道，作者可任意组合
  （怪盗ブルブラン、X幻影等），不影响 bank 判定；
- **(场景, 函数, talk_num) 的唯一性**：一个键可挂多行（同段话拆多文本框），
  但**同一键的 bank 零冲突**（29,368 个带语音键实测）——键→bank 唯一。

## 5. 查询工具

```bash
# vid → 单条台词完整定位（场景/函数/块/talk_num/speaker/身份）
uv run python review_agent/rt.py vid 0010350604

# bank(=vid前3位) → 全场景角色档案（身份/槽位分布/显示名/场景清单/乱入记录）
uv run python review_agent/rt.py bank 005


```

数据文件（`SkyStructureAligner/data/`）：

| 文件 | 内容 |
|---|---|
| `evo_speaker_names_sc.json` | 知识库：banks（名字/状态/特殊计数）、char_id↔bank、T_NAME 全表 |
| `evo_talk_bank_index_sc.json` | 29,368 个 (场景/函数/talk_num) → bank |
| `evo_bank_index_sc.json` | bank → 完整档案（含 special_identity_occurrences 明细） |

更新知识库：`build_evo_bank_index_pure.py` 从 pure 结构 + cast 表重建（charid 投票 /
cast 表反查 / 名框投票三层命名，`MANUAL_CN` 表维护人工中文名），重跑该脚本后
rt.py 缓存版本会自动刷新。

## 6. 给匹配流程的结论

1. **说话人身份一律以 bank 为准**；`0x10x` 行可另用 T_NAME 交叉验证；
2. 槽位名（场景字符串表）只对"城镇 NPC 闲聊"用法可靠，事件场景一律不用；
3. bank 与映射说话人码不符的行（s4 的"链内角色不符"）是真警讯：
   要么 Remake 改派，要么错配，交人工复核；
4. 群众/共用 bank（无全局角色 ID、多人共用）需按"场景×角色段"判定，
   详见 `docs/voice_lookup.md`。

> 原生指令格式、MBIN V 标记、cast/chip 映射等解包层细节不在本文范围（属逆向工具链）。
> 本文只描述"数据怎么读"的判定模型；数据资产由 `evo_structure_pure_sc.json` 等分发文件提供。
